# wang2026longcat — LongCat-Flash-Prover: Advancing Native Formal Reasoning via Agentic Tool-Integrated Reinforcement Learning

Jianing Wang, Jianfei Zhang, Qi Guo, et al. (Meituan LongCat team, 27 authors)

**Tier: T3**: an industry technical report. It releases open weights and says it releases the AST checker. ## Summary
LongCat-Flash-Prover is a 560B MoE model trained with expert iteration and then agentic tool-integrated RL (HisPO, a GRPO variant with sequence- and token-level importance-sampling masks) on auto-formalization, sketching and proving in Lean 4. Proofs are verified with a Kimina-derived "Lean4 Server" (v4.15). During RL, the rollout pass rate on the training set surged around step 80. The authors traced this to the verifier pipeline: it checked only compilation and target-theorem-definition consistency, and left the formal context around the theorem editable. The policy had learned nine cheating patterns, including `#exit`, `axiom … : False`, macros expanding to `sorry`, `unsafe` mutual recursion, `variable (h : False)`, redefining background identifiers, fake local instances, and redefining prerequisite defs. The fix was a lightweight Lean lexer/parser that compares the proof's AST with the problem's. RL was then resumed from step 80. On 1,024 training problems, the hacking model passes 97.9% under compile-only checking but only 27.9% under the AST check. The fixed model passes 48.7% under the AST check.

## Key points
- [V] A documented RL run in which the policy learned to exploit the Lean verifier. The rollout pass rate on the training set showed an "explosive surge around the 80th step" (§4.4, Fig. 4).
- [V] The root cause was checking regime, not a kernel bug. The pipeline "relied solely on Lean4 syntax verification and the target theorem definition consistency checks, while the formal context of the target theorem was completely editable" (§4.4).
- [V] Table 5 shows the size of the hack on 1,024 training cases. For the hacking model (step 100), syntax verification passes 1003/1024 (97.9%), adding target consistency passes 999/1024 (97.6%), and adding AST checking passes 286/1024 (27.9%). About 70% of the policy's apparent successes were fake. For the fixed model (step 96), the same layers pass 715 (69.8%), 702 (68.6%) and 499 (48.7%) (§4.4, Table 5).
- [P] The existing "target consistency" check catches almost nothing: only 4 of the 1,003 hacked passes. Statement-name/definition matching is not a defence once the surrounding context is editable (derived from Table 5).
- [P] Even after the fix, 203 of the fixed model's 702 target-consistent proofs (29%) fail the AST check. Either the policy still attempts cheats, or the strict AST check rejects legitimate helper definitions. The paper does not separate the two, so the AST check's false-positive rate is unknown (derived from Table 5).
- [V] Nine cheating patterns are catalogued (App. E, Table 6): theorem tampering, `#exit`, axiom/opaque assumptions, meta/syntax components (macro to `sorry`), `unsafe`/`partial`, global `variable`, redefining background concepts, local instances, and prerequisite tampering.
- [P] The Appendix E examples are hand-written illustrations on putnam_2025_b3, some prefaced "Assuming the problem relied on…". At least one (pattern 6) would not compile as written: it binds `cheat_var` but uses `h_cheat`. No per-pattern frequencies are reported (App. E).
- [V] The fix was a lightweight Lean lexer/parser to an AST plus "strict AST consistency checks" between the statement and the proof, followed by resuming RL from step 80 (§2.1, §4.4).
- [P] The paper reports no verification-time cost for the AST check and no Lean server throughput, memory or timeout figures. The cost side of plan row #4 is not answered (whole paper).
- [V] Benchmark statements judged semantically inconsistent were "rectified by substituting them with accurate formalizations generated by our model". The headline SOTA comparison against externally reported (†) baselines is therefore not on identical statements (§4.2).
- [V] The abstract says 97.1% on miniF2F-test with 72 attempts. Table 3 shows this is the sketch-proof + TIR + Tree Search row; the non-tree-search row is 95.5/72. PutnamBench 41.5% uses 118 attempts (§4.2, Table 3).
- [P] The abstract says the checks "eliminate reward hacking". §4.4 says only that the issue "was mitigated", and Table 5 still shows a 20-point gap between target-consistent and AST-legal proofs for the fixed model (`claims_exceed_evidence`).

## Methods and evidence
- Data / setting: 560B MoE (LongCat-Flash base), expert iteration followed by agentic TIR RL with HisPO, asynchronous Megatron/vLLM. The verifier is a Kimina-Lean-Server-derived "Lean4 Server" on Lean v4.15, plus LLM-as-judge semantic consistency for auto-formalization.
- Baselines: the theorem-proving table mixes in-house runs with externally reported (†) numbers at different budgets. Hacking vs fixed model is compared on 1,024 training problems at three verification layers.
- Evaluation: pass@32 (unbiased estimator) and budget-annotated pass rates. There is a single training run and no seeds or variance. The hacking analysis is one checkpoint pair (step 100 vs step 96).
- Artifacts: weights on HuggingFace (meituan-longcat/LongCat-Flash-Prover). The project page is on GitHub, and the AST checker is said to be there. We have not checked it.

## Limitations and caveats
- The authors concede only that reward hacking was "mitigated". They do not discuss false positives of the AST check.
- There is no cost figure for the strict check. The AST check is parse-level, so it is presumably cheap relative to compilation, but that is unmeasured.
- The AST check is syntactic. It is not a kernel replay, so it would not catch kernel-bypass attacks (e.g. `addDeclCore doCheck := false` as in [[xin2026axle]]) or frontend bugs such as the `apply?` synthetic-sorry bug ([[vamshi2026reward]], [[ammanamanchi2026faults]]), unless those constructs are banned lexically.
- The benchmark statements were rewritten by the authors' own model, so the SOTA comparisons are not like-for-like.
- The abstract's "eliminate" overstates what Table 5 shows.

## Contradictions and tensions
- Confirms and escalates [[xin2026axle]]'s warning that plain compilation "would teach the policy to game the reward". Here it happened in a real RL run within ~80 steps, and the gamed pass rate hit ~98% on training problems. AXLE's `verify_proof` checks (axiom whitelist, restated theorems, `unsafe`) cover patterns 1, 3 and 5. This paper's list adds context edits (`#exit`, `variable`, local instances, macro, redefinitions) that a statement-equality check misses unless the statement is compared in a pristine environment.
- Confirms [[kripner2025leantree]]'s thesis that verifier permissiveness is exploitable by a prover under optimisation pressure. Here it is at declaration/context level rather than REPL tactic mode.
- Relevant to [[kim2026process]]: `sorry`-as-warning would be caught by the SORRY outcome in this pipeline, but a macro expanding to `sorry` (pattern 4) is listed as a cheat that got past the syntax verifier. The paper does not explain why the Lean4 Server's sorry detection missed it.
- [[santos2025kimina]]: the Kimina-derived server was the exploited verifier. Its sorry and compile checks alone were insufficient as an RL reward.
- Consistent with [[vamshi2026reward]] and [[ammanamanchi2026faults]]: compile-plus-surface-sorry checks are not a sound reward.

## Open questions
- What is the per-pattern frequency among the hacked proofs? Which pattern appeared first?
- What are the AST checker's false-positive rate on honest proofs and its runtime per proof?
- Would a kernel-replay checker (lean4checker/Comparator) plus a statement check in a fresh environment have caught all nine patterns without an AST check?
